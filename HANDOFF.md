# VSD M18 pad controller — handoff

For anyone picking this up: another agent, or a human reviewer. Read this first, then `ROADMAP.md` (what to build next)
and `README.md` (the user-facing quick start). Last updated after the **folders** feature.

## 1. What this is

The user owns a "VSDinside" **VSD M18**: a Stream Deck-style macro pad (15 LCD keys in a 5x3 grid plus 3 round
buttons). They first thought it was a Steam Deck handheld. The vendor software (VSD Craft) was buggy, so we replaced it
with our own Python app that drives the pad directly over USB HID. **It runs daily on the user's PC**, starts at login with a
tray icon, and has a local web settings page.

Working directory `C:\code\vsdpad`. Windows 11, Python 3.10, PowerShell. Run `python app.py --gui`.
The user is **not a developer**: tell them exactly what to click or run, one step at a time.

Startup shortcut: `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\VSDPad.lnk` runs `pythonw.exe app.py` in `C:\code\vsdpad`.

## 4. How to run, test and develop safely

```
python tests\run_all.py                          # compile everything + both test suites (132 checks). Needs no pad.
python app.py --check                            # validate config + plugin actions (also flags folder keys pointing at missing pages)
python app.py --press 2 [--page 2]               # run one key's action without the pad (round-button id works too)
python app.py --gui-only --config <COPY>.json    # settings server without a pad, on a COPY of the config (default port 8765, else next)
python app.py --gui | --no-tray | --draw | --test
```

**Rules that matter:**
- The user's real copy holds the mutex `Local\VSDPadController` and the pad. Dev/test runs use a separate mutex (`.dev`) when given
  `--check/--press/--gui-only/--config`. **Always test against a copy of `config.json`**: the GUI saves for real.
- Only one process can drive the pad. VSD Craft must stay closed. Stop a specific PID, never all `python.exe`.
- You cannot see the pad. Anything visual needs the user to look and report; ask concrete questions ("does the bottom border touch the top edge?").
- **Secrets:** Home Assistant token and Hue app key live in plain text in `config.json` (local file). The user types them into the
  Plugins tab. Never ask them to paste tokens into chat and never read or print those values.
- The GUI was tested by driving the page with ad-hoc scripts in a browser (select, edit, drag, save, plugin buttons, folders). Those scripts were not kept, so there are no automated UI tests yet (see ROADMAP R12).
- This folder is a git repository (branch `main`). `.gitignore` keeps `config.json`, its backups and `vsdpad.log` OUT of git because they hold the
  user's secrets. **Before every commit run `git status` and make sure no config/log file is staged.** A fresh clone has no `config.json`:
  copy `config.example.json` to `config.json` (secret-free starter layout; regenerate with `python tests\make_example_config.py`).
- Real-device checks: user stops their copy (Ctrl+C or Task Manager), starts `python app.py --gui`, reports what they see.

## 5. Hardware protocol (verified on the real device)

USB `VID 0x5548, PID 0x1000`, "HOTSPOTEKUSB HID DEMO" (Mirabox/Ajazz-style). Interface 0 (usage page 0xFFA0) is the control channel.

- Output reports are 1024 bytes (report id `0x00` + 1024). Commands begin `CRT\x00\x00`: `DIS` wake; `LIG\x00\x00<0-100>` brightness;
  `CLE\x00\x00\x00<0xFF>` clear; `STP` commit; `BAT\x00\x00<len u16 BE><index>` then the JPEG in 1024-byte chunks;
  `CONNECT` keep-alive every ~5 s.
- LCD keys are **72x72 JPEG**, rotation 0. The bezel hides roughly the outer 4-5 px, so keep borders/brackets inset (about 28/216 for packs).
- Input: 512-byte reports `ACK\x00\x00OK\x00\x00` + id + state (1 press, 0 release). **Use non-blocking reads** (blocking timeouts caused `read error` loops).
- **Rows:** config/GUI slots run top-to-bottom (1-5 top, 6-10 middle, 11-15 bottom). The pad's image index runs bottom-to-top, so
  `hardware.image_index(slot)` flips rows when sending. **Press ids equal slots directly** (`press_to_slot` is the identity).
  This was wrong in an early version and the user caught it on the device; it is now confirmed.
- Round buttons report raw ids 37, 48, 49 (`0x25, 0x30, 0x31`); positions are assignable in the GUI (Identify on pad).
- The bottom row of screens needs a +8 px downward picture offset on this unit (`row_offset: [0, 0, 8]`); cause unknown.

## 6. Architecture notes

**Config (v4)**, `store.py`: `pages: [{id, name, folder, keys: {"1".."15": spec}}]` (1-24; first page is never a folder; ids unique `[a-z0-9]{3,16}`),
`round: {"<id>": spec}` (global, shared by every page), `round_buttons: [id, id, id]`, `plugins: {id: settings}`, `icon_pack`, `row_offset`,
`brightness`, `rotation`. A key spec is `{icon, label, color:[r,g,b], repeat?, action?: {plugin, action, params}}`. Migration chain v1 -> v2 -> v3 -> v4
(each writes a backup `config.json.bak` / `.v2.bak` / `.v3.bak` once). Writes are atomic (`os.replace`); `Store.version` bumps on every save and the pad loop redraws.

**Pad loop** (`app.py`): one thread; connect, `configure` pages, draw the current page, then poll: keep-alive every 5 s, redraw when `store.version`
or `pagestate.version` changes, read events, resolve a press via `store.spec_for_press(cfg, page, id)` (LCD keys from the current page, round buttons global),
run the action on a thread (and a repeat thread while held if `repeat`). Publishes `status.pad_connected`, `last_press`, `press_seq`.

**Plugins**: contract in `plugins/base.py` (`settings`, `buttons`, `actions` with typed `params`, `run()`, `api()`). Param kinds `text|number|select|choice`.
`choice` calls `plugin.api(<name>, {domains?})`; the special `api: "@pages"` is filled by the page from the config. `api()` may return `_save` to persist
settings (Hue pairing). Discovery is automatic for `plugins/*.py` exposing `PLUGIN`.

**Pages and folders** (`pagestate.py`): folders are pages with `folder: true`. `open(id)` pushes the trail, `back()` pops, Next/Previous skip folders
(from inside a folder they step from the page it was opened from), `goto(n)` clears the trail. `configure()` keeps position by id when pages change.

**Server** (`server.py`): `127.0.0.1:8765` (+10 fallback ports; exclusive bind). Endpoints: `GET /`, `/api/state` (secrets masked), `/api/status`, `/api/preview.png`,
`/api/pack_preview.png`; `POST /api/config`, `/api/test`, `/api/plugin/<id>/settings`, `/api/plugin/<id>/api/<name>`.
Checks: Host must be `127.0.0.1:<port>`/`localhost:<port>`, Origin (if sent) must be local, POST needs `application/json`, body <= 1 MB, config validated before save.

**Themes** (`iconpacks.py`): a pack = `icons/<id>/pack.json` + `wallpaper.png` (1272x744: tile 216, gap 48). Each key gets its wallpaper slice, a dark overlay, a glowing glyph,
an outlined label and HUD brackets (blank keys get faint brackets, so the pad reads as one theme). `row_offset` shifts the whole key picture per row.

## 7. Security and safety model (review this)

- Local web API has **no authentication**; protection is the localhost bind plus Host/Origin/Content-Type checks (stops web pages and DNS rebinding,
  not other programs running as the user). Actions can launch commands (`system.launch` uses `shell=True`) and call webhooks; anyone who can reach the API can trigger them.
- Hue: the bridge uses a self-signed cert, so TLS verification is skipped **only** for private-network addresses (`.local/.lan/.home` or RFC1918/loopback). Discovery uses normal TLS.
  Ids are validated before going into URL paths. HA token is sent only to the user's saved URL; non-http(s) URLs are rejected.
- Secrets are stored unencrypted in `config.json`. Windows DPAPI (`CryptProtectData`) would be an easy hardening step.
- Icon pack import (zip) is not built; when added it needs zip-slip protection, size limits, PNG/JSON only.

## 8. Known issues and open questions

1. **Occasional pad connection drop (unexplained).** `vsdpad.log` shows one in ~40 min since logging began: `OSError: read error`
   after **272 s connected, 195 s after the last key press** (keep-alive was running), then `open failed` once, then a clean reconnect 5 s later and redraw.
   Windows logged no USB disconnect. Hypotheses: the pad has an idle behaviour near 3 minutes, or the keep-alive is not what the firmware expects.
   Ideas: log more around the event, try other keep-alive intervals, debounce the "disconnected" status for a few seconds, redraw less aggressively on reconnect.
2. The bottom-row +8 px offset is a workaround, not an explanation.
3. Folders and the v3 -> v4 migration have not run on the real pad yet.
4. Hue: only the v2 (CLIP) API, so the old square v1 bridge is unsupported. HA: REST only, no websocket, so no live state yet.
5. The GUI has no automated tests; there is no CI, no type checking, no packaging (the user needs Python installed).
6. Unfinished edges: copy/reorder pages, per-folder theme, pack import, named per-icon PNGs, the 8-bit `retro` pack.

## 9. Questions for a reviewer

- Is the unauthenticated local API acceptable, or add a per-session token / require a header the page gets at load?
- Config migration: is the "backup once per version, atomic write" approach enough? Any failure mode that could lose a layout?
- Plugin contract: stable enough to document for third parties? (`api()` free-form results, `_save`, `@pages` special-case.)
- Pad loop robustness: reconnect/redraw behaviour, thread safety of `status`/`pagestate`, repeat threads.
- Anything in `web/index.html` that could be abused by a hostile config value (labels, icons, plugin names are rendered with `textContent`/`h()`, never `innerHTML`).
